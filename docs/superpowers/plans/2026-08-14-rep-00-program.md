# TRU Rep → the training library — program plan

> **For agentic workers:** this is the **program spine**. It reviews what exists, fixes the running
> order, and holds step-level plans for the phases that don't have one yet. Phases 1, 2 and 3 already
> have full task-by-task plans — execute those files, not this one, when you reach them. Use
> `superpowers:subagent-driven-development` or `superpowers:executing-plans` per phase. Steps use
> checkbox (`- [ ]`) syntax.

**Goal:** Turn the Rep tab from a five-module certification course into a training library big enough
to onboard a whole team — every training Eric currently presents live becomes either permanent
reference material or a self-paced module, and the ones that teach clicking (Day 1 first) are graded
by making the learner actually do the work on the real screens.

**Architecture:** Keep the existing card/lesson/progress engine and extend it in four places — a
*shelf* above modules (tracks, assignment, search, certificates), a *learner spine* so leaders can be
learners, a *reference* rendering of every module that is never gated, and one new card type (`sim`)
that composites live form controls over real product screenshots and refuses to advance until the
record is correct.

**Tech Stack:** React 18 + Vite (`web/`), Cloudflare Worker TypeScript (`worker/`), Supabase/Postgres
(`db/`), shared pure TypeScript with vitest node-environment tests (`shared/`), Anthropic Haiku 4.5
for rubric grading, Retell for voice roleplay.

**Spec:** `docs/superpowers/specs/2026-08-14-rep-training-library-design.md`

## Global Constraints

Every task in every phase inherits these.

1. **Answers never reach the browser.** `rep_scenarios.answer`, `rep_questions.answer` and every
   rubric string stay server-side. The client receives `spec` only. There is a test whose whole job is
   to fail if a check definition, an expected value or a rubric element appears in a browser payload.
2. **Screenshot provenance is binding.** Only images marked `OFFICIAL` or `DERIVED REDACTED` in
   `~/Documents/Codex/2026-08-08/zillow-preferred-day-one-framework/work/production/screenshot-inventory.md`
   may be baked into a skin. `LIVE DEMO` and `RECAPTURE` images are blocked until an approved,
   redacted current-team capture exists. No product screen is ever recreated by hand.
3. **`skinId` stays pure data.** No component, check or scenario may hardcode a vendor's name, colour
   or layout. Swapping `fub-2026-08` for `tru-generic` must require zero code changes.
4. **Seven surfaces, then stop.** People list, Smart Lists rail, contact profile, activity panel,
   notes, tasks, contact bar. Any Follow Up Boss feature the Day 1 script does not exercise is out of
   scope — including "it's only five more minutes" additions.
5. **Deterministic checks only where exactly one answer is right.** Everything human goes to the
   rubric and is scored on required elements, never string equality. A check that fails correct work
   destroys the whole library's credibility in one session.
6. **Every content claim carries a source line.** Numbers, standards and scripts are transcribed from
   a frozen source file with the line cited in the module's manifest. Nothing is invented.
7. **No module ships whose only proof is multiple choice.** See §3.1 of the spec.
8. **Deploy discipline.** `.env.production` is gitignored and a fresh checkout bakes a dead database
   URL into the bundle. The Worker deploys only from `main`. `main` moves under you when Codex lands
   commits from the laptop — fetch and merge before every push.
9. **Additive, idempotent SQL** in the house style of `db/hq_rep_*.sql`. Applied through the Supabase
   MCP connector, never handed over as SQL to paste.

I read the running code, not the docs. Rep is in better shape than it feels; the problem is that every
line of it assumes *one course with five modules*, and that assumption is load-bearing in about nine
places.

### What's already good

| Piece | Where | Verdict |
|---|---|---|
| Typed lesson cards — 12 kinds | `web/src/lib/api.ts:130` | Genuinely good. Extensible without a rewrite. |
| The advance gate | `AgentCourse.tsx:538`, `:571` | The hook the whole simulator hangs on. A new card type inherits gating for free. |

| Voice roleplay + LLM rubric grading | `worker/src/practice.ts` (Retell → Haiku, ALMS breakdown) | Production-ready and badly underused — it's locked behind "pass all five modules". |

### What blocks the library — nine concrete findings

1. **A leader cannot take a module at all.** `rep_progress.agent_id` references `agents(id)`; a team
   leader is a `memberships` row. `loadCourse(agent.id)` (`AgentCourse.tsx:56`) has no identity to
   pass for them. Eric's ask — *bosses and agents both have to pass* — is blocked on this, so it is
   Phase 1 Task 1, not a nicety.
2. **A module with no quiz is unopenable.** `disabled={!m.qs.length}` (`AgentCourse.tsx:125`) and
   `setView(m.qs.length ? 'lesson' : 'home')` (`:80`). A pure reference document — the exact thing
   "let them come back and re-read Day 1" needs — cannot exist in the data model today.
3. **The home screen is a flat list with hardcoded copy.** `'All five modules down'` (`:97`),
   `Ring passed/total` over every module in the org. At sixteen modules it reads as a wall; at fifty it
   is unusable. No tracks, no tags, no search, no filter, no duration, no level, no cover.
4. **The Live Sim is gated behind *every* module.** `simUnlocked = allMods` (`:75`). In a library that
   spans four programs, "finish everything Eric has ever written" is the wrong unlock condition. It
   must become per-track.
5. **The certificate is computed at render time, not issued.** `certified = allMods && simPassed`
   (`:78`) — recomputed on every load, stored nowhere, not visible to the leader, and it silently
   un-certifies the moment a sixth module is published.
6. **Every module proves mastery the same way.** Cards then four multiple-choice questions. That is
   why it reads as compliance training. Nothing in the engine prevents better proof; nothing in the
   content uses it.
7. **The best content isn't in the app.** 36 slides / 940 lines of Day 1 script, a four-contact
   scenario pack with answer keys, and 46 provenance-tracked screenshots live in
   `~/Documents/Codex/2026-08-08/zillow-preferred-day-one-framework/`. Another ~20 finished trainings
   live in Google Drive (see Part B). The app has five modules.
8. **There is no assignment.** A leader cannot say "these six people, this track, due Friday" — the
   thing an onboarding library exists to do.
9. **`estMinutes` is a guess from card count** (`AgentCourse.tsx:41`). Duration is a browsing filter in
   a library; it needs to be an authored field.

### The two things Eric asked for, stated as acceptance criteria

**Ask 1 — follow-up reference.** An agent who sat through a live training can open Rep afterwards and

conditions — set the right stage, write a note that would survive a handoff, schedule the task they

#### Task 0.2: Close the `eventExists` gap between Phase 2 and Phase 3

Phase 2's check contract defines six check types —
`equals | taskExists | noteExists | multiselect | eventBefore | rubric`
(`2026-08-14-rep-02-practice-crm.md:349`). Phase 3's scenarios for Z4 and Z5 use a seventh,
`eventExists`, which nothing defines. Two checks would fail to parse at seed time, a week into the
authoring phase, for a reason nobody would look for.

`eventBefore` asserts *ordering* (open the activity panel before editing). `eventExists` asserts an
action *happened at all* — "you searched by phone number", "you opened the activity panel" — which is
how Z4 proves *find Maya two ways*. It is genuinely a different assertion, so add it rather than
rewrite the scenarios.

**Files:**
- Modify: `docs/superpowers/plans/2026-08-14-rep-02-practice-crm.md` — Task 3

- [ ] **Step 1: Extend the `Check` union in Phase 2's Task 3 "Produces" block**

```ts
type Check =
  | EqualsCheck | TaskExistsCheck | NoteExistsCheck
  | MultiselectCheck | EventBeforeCheck | EventExistsCheck | RubricCheck;

/** Asserts an action occurred at least `min` times (default 1), optionally matching a payload
 *  subset. `EventBefore` asserts ordering; this asserts occurrence. */
interface EventExistsCheck {
  id: string; type: 'eventExists'; weight: number; fail: string;
  event: SimEvent['type'];
  where?: Record<string, string | number | boolean>;  // shallow subset match on event payload
  min?: number;                                        // default 1
}
```

- [ ] **Step 2: Add the two tests to Phase 2's Task 3 test block**

```ts
describe('eventExists', () => {
  const check: Check = { id: 'phone', type: 'eventExists', weight: 10,
    event: 'search', where: { mode: 'phone' },
    fail: 'You found her by name. Find her by phone number too.' };

  it('passes when a matching event occurred', () => {
    const events: SimEvent[] = [
      { type: 'search', mode: 'name',  q: 'Maya' },
      { type: 'search', mode: 'phone', q: '253-555-0148' },
```

- [ ] **Step 3: Add the implementation note to Phase 2's Task 3 prose**

> **`eventExists`** counts events whose `type` matches and whose payload contains every key/value in
> `where` (shallow, `===`). Passes when the count is at least `min` (default 1). It never inspects
> `SimState`, so it works for actions that leave no trace in the record — searching, opening a panel,
> clicking a phone number.

```ts
/** Where a module card should go when clicked. A module with cards is always readable, even

export function moduleTarget(m: CourseModule): 'lesson' | 'handbook' | null {
  const hasCards = (m.cards?.length ?? 0) > 0;

  if (m.kind === 'reference') return hasCards ? 'handbook' : null;
  if (hasQuiz) return 'lesson';
```

```ts
import type { LessonCard } from '../web/src/lib/api';

export interface SearchDoc {
  moduleId: string; trackId: string | null; title: string;
  fields: Array<{ text: string; norm: string; weight: number; cardIndex: number | null }>;
}
export interface SearchHit {
  moduleId: string; trackId: string | null; title: string;
  snippet: string; cardIndex: number | null; score: number;
}

const norm = (s: string) => s.toLowerCase().replace(/[^a-z0-9\s]+/g, ' ').replace(/\s+/g, ' ').trim();

/** Every string a card can carry. Add a case when a card type gains a text field. */
function cardText(c: LessonCard): string {
  const parts: Array<string | undefined> = [
    (c as { title?: string }).title, (c as { body?: string }).body,
    (c as { label?: string }).label, (c as { big?: string }).big,
    (c as { prompt?: string }).prompt, (c as { why?: string }).why,
  ];
  const lines = (c as { lines?: string[] }).lines ?? [];
  const steps = (c as { steps?: string[] }).steps ?? [];
  const choices = (c as { choices?: string[] }).choices ?? [];
  const turns = ((c as { turns?: Array<{ text?: string }> }).turns ?? []).map((t) => t.text ?? '');
  return [...parts, ...lines, ...steps, ...choices, ...turns].filter(Boolean).join(' ');
}

export function buildSearchIndex(
  modules: Array<{ id: string; trackId: string | null; title: string; tags?: string[] | null;
    cards?: LessonCard[] | null }>,
): SearchDoc[] {
  return modules.map((m) => ({
    moduleId: m.id, trackId: m.trackId, title: m.title,
    fields: [
      { text: m.title, norm: norm(m.title), weight: 10, cardIndex: null },
      { text: (m.tags ?? []).join(' '), norm: norm((m.tags ?? []).join(' ')), weight: 6, cardIndex: null },
      ...(m.cards ?? []).map((c, i) => {
        const t = cardText(c);
        return { text: t, norm: norm(t), weight: 1, cardIndex: i };
      }),
    ],
  }));
}

export function searchLibrary(index: SearchDoc[], q: string): SearchHit[] {
  const nq = norm(q);
  if (!nq) return [];
  const hits: SearchHit[] = [];
  for (const doc of index) {
    let best: SearchHit | null = null;
    for (const f of doc.fields) {
      const at = f.norm.indexOf(nq);
      if (at < 0) continue;
      const score = f.weight * 100 - at;
      if (best && best.score >= score) continue;
      const raw = f.text;
      const from = Math.max(0, at - 40);
      best = {
        moduleId: doc.moduleId, trackId: doc.trackId, title: doc.title,
        snippet: (from > 0 ? '...' : '') + raw.slice(from, at + nq.length + 60).trim() +
                 (at + nq.length + 60 < raw.length ? '...' : ''),
        cardIndex: f.cardIndex, score,
      };
    }
    if (best) hits.push(best);
  }
  return hits.sort((a, b) => b.score - a.score);
}
```

> The snippet is sliced from `text`, not `norm`, so the learner sees the real punctuation and casing.
> Offsets differ slightly between the two after normalisation; a plus-or-minus 40-character window
> absorbs that, and the test asserts containment, not exact bounds.

## Part E — The quality bar

Eric's business benchmark is the constraint, so make it checkable rather than aspirational. Every
module ships against this list or it does not ship.

**Content**
1. One objective. If it needs two, it is two modules.
2. 6-10 minutes. Longer means it was never scoped.
3. Opens with a hook — a real consequence, not a learning objective.
4. Ends with a proof step that is not four multiple-choice questions.
5. Shows "what good looks like" as a real artifact — an actual note, an actual task, an actual record.
6. Every number carries a source line in the track's manifest.
7. No lorem, no stock photography, no clip art. Real product screenshots with provenance, or nothing.

**Craft**
8. Cover art, duration and level on every card in the shelf. Nothing browses as untitled grey.
9. The TRU dark palette — warm gold `#a9791f` on near-black, per `web/src/truHqDark.css`. No new
   accent colours invented per module.
10. The handbook prints to a clean PDF: no navigation chrome, no dark background, no broken images.
11. Motion is used to reveal, never to decorate. Existing `fu` fade-up classes only.

**Fairness — the thing that decides whether people trust it**
12. A check that fails correct work is a P1 defect, treated as a bug, not as learner error.
13. Every `fail` message teaches without leaking the answer. Priya's stage check says *"Appointment set
    claims a meeting that was never booked"* — not *"the answer is Spoke With"*.
14. Hints escalate; they never solve.
15. Retries are unlimited, and the record shows attempts, because attempts are information.

**Accessibility — a real risk, because the simulator is a picture**
16. Every live control composited over a screenshot has a visible label or an `aria-label`, and is
    reachable in tab order. The screenshot itself carries an `alt` that describes the screen state, so
    the exercise is not a blank wall to a screen reader.
17. No information conveyed by colour alone in check results — pass/fail carries a mark and words.
18. The handbook is plain semantic HTML: real headings, real lists, real links.

## Part F — Risks

Ordered by how likely each one is to actually eat this project.

1. **Cloning Follow Up Boss too far.** Seven surfaces, then stop. Every "it's only five more minutes"
   addition is the failure mode. Mitigation: constraint #4 is in every plan's global constraints, and
   any new surface requires an explicit spec amendment.
2. **Content debt — the shell outruns the writing.** Phases 3 and 5 are authoring hours, not
   engineering hours, and they are the ones that slip. Mitigation: Phase R makes the Drive backlog
   *useful as reference* in three days, so the library has real breadth long before every deck is
   converted to a graded module.
3. **Brittle grading.** One check that fails correct work destroys trust in a single session, and it
   does not come back. Mitigation: deterministic only where exactly one answer is right; Phase 4 Task
   4.5's golden-note guard; Phase 3 Task 9's pilot metric "most-failed check".
4. **Answers leaking.** Mitigation: `spec` to the browser, `answer` never, and a test whose whole job
   is to fail if a check definition, an expected value or a rubric element appears in a browser
   payload.
5. **The screenshots go stale.** Follow Up Boss will redesign. Mitigation: skins are versioned by date
   (`fub-2026-08`); scenarios reference `skinId` and nothing else; re-capture is a skin swap, not a
   content rewrite. Put a recurring six-month re-capture check on the calendar.
6. **Third-party imagery outside Eric's own teams.** Using FUB's published documentation inside Eric's
   own client teams is ordinary. Selling Rep to another brokerage with FUB chrome baked in is not.
   Mitigation: Phase 8 Task 8.2 builds the generic skin, and `skinId` stays pure data so it can be
   swapped without touching a scenario, a check or a component.
7. **Accessibility of a screenshot-composited UI.** Genuinely hard, and easy to discover too late.
   Mitigation: Part E items 16-18 are Phase 2 acceptance criteria, not a later pass.
8. **Deploy discipline.** `.env.production` is gitignored and a fresh checkout bakes a dead database
   URL into the bundle; the Worker deploys only from `main`; `main` moves under you when Codex lands
   commits from the laptop. Mitigation: fetch and merge before every push, and verify the built bundle
   points at the live database before publishing.
9. **Two Rep copies on disk.** `~/Desktop/truhq/landing/web/src/pages/Rep.tsx` is a stale 14 KB
   version of the 50 KB file in `pulse`. Nothing in this program touches `landing`. Confirm before any
   edit that you are in `~/Desktop/truhq/pulse`.
